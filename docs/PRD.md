# PRD — Платформа оценки инженерного персонала бурового сервиса

Кодовое имя: **Nestro Assessment Platform** (далее — Платформа).
Версия документа: 1.0. Язык интерфейса первой версии: русский.

---

## 1. Назначение и границы

Платформа — корпоративная система дистанционного тестирования и оценки кандидатов
на инженерные должности в строительстве нефтяных и газовых скважин.

Платформа **не** является онлайн-опросником и **не** является психодиагностическим
инструментом. Она измеряет профессионально значимые характеристики инженерного
мышления и выдаёт **систему поддержки решения**:

```
рекомендуемая профессиональная оценка
  + доказательства (цитаты из ответов кандидата)
  + зоны риска
  + уровень уверенности (confidence)
```

Кадровое решение принимает человек. Платформа никогда не печатает «принять» /
«отказать» и не выполняет автоматических кадровых действий.

### 1.1. Что оценивается

| # | Характеристика | Слой измерения |
|---|---|---|
| 1 | Способность предотвращать осложнения | SJT, Kelly, rubric `PREVENTION` |
| 2 | Причинно-следственное мышление | SJT, argumentation, rubric `CAUSAL` |
| 3 | Системность | SJT multi-stage, Kelly laddering |
| 4 | Анализ тенденций | SJT с динамикой параметров |
| 5 | Качество принятия решений | SJT, обязательные поля «что проверить первым» |
| 6 | Отношение к риску | SJT, red flags, rubric `RISK` |
| 7 | Понимание границ полномочий | SJT «кого уведомить / когда эскалация» |
| 8 | Своевременность эскалации | SJT, hard-gate |
| 9 | Взаимодействие со смежными сервисами | SJT интегрированного сервиса |
| 10 | Ориентация на конечный результат скважины | laddering (глубина смысла) |
| 11 | Профессиональная рефлексия | self-rating + gap-анализ E10↔E9 |
| 12 | Извлечение уроков | отдельная компетенция `LESSONS` |
| 13 | Качество аргументации | argumentation layer (слой C) |
| 14 | Фактический полевой опыт | требование примера из опыта в каждой триаде |
| 15 | Техническая зрелость | агрегат `OPERATIONAL_MATURITY` |

### 1.2. Что система обязана НЕ делать (жёсткие запреты, покрыты тестами)

* не ставить психологические/медицинские диагнозы — в rubric и промптах
  запрещены диагностические формулировки; `docs/KELLY_METHOD.md` §9;
* не использовать возраст, пол, национальность, религию, политические взгляды,
  здоровье, семейное положение — эти поля отсутствуют в модели данных
  (`Candidate` хранит только ФИО, e-mail, должность, стаж, источник);
* не выдавать вердикт «хороший/плохой человек» — категории результата нейтральные
  квалификационные (см. §18 мастер-требований, реализация `ScoreBand`);
* не принимать окончательное кадровое решение — `EmploymentOutcome` заполняется
  только человеком с правом `employment_outcome:write`;
* цвет в UI не кодирует человека как «плохого» (см. `docs/ARCHITECTURE.md` §UI).

## 2. Роли и пользовательские сценарии

| Роль | Ключевые сценарии |
|---|---|
| **SuperAdmin** | управление пользователями и ролями, все права |
| **AssessmentAdmin** | конструктор тестов, веса, rubric, версии, пороги, промпты |
| **HR** | приглашения, дашборд, отчёты, сравнение, экспорт |
| **TechnicalExpert** | human review, комментарии, корректировка баллов, вопросы к интервью |
| **Viewer** | чтение отчётов и аналитики без правок и без PII-экспорта |
| **Candidate** | прохождение теста по одноразовой ссылке (без пароля) |

### 2.1. Сценарий HR (основной)

1. HR создаёт приглашение: ФИО, e-mail, должность, версия ассессмента, дедлайн.
2. Система выдаёт одноразовую защищённую ссылку (токен виден один раз).
3. HR отправляет ссылку (в MVP — вручную/через SMTP, если настроен).
4. HR наблюдает статусы: `CREATED → SENT → OPENED → IN_PROGRESS → COMPLETED → REVIEWED`.
5. После завершения — асинхронная LLM-оценка → `SCORED` → карточка кандидата.
6. HR открывает отчёт, при необходимости отправляет на экспертную проверку.

### 2.2. Сценарий кандидата

1. Открывает ссылку → страница приглашения: должность, структура теста,
   ориентировочная длительность, правила, согласие на обработку данных.
2. Секции по порядку: `INTRO → KELLY_TRIADS → REPERTORY_GRID → LADDERING →
   SJT_CASES → ARGUMENTATION → SELF_RATING → FINISH`.
3. Каждый значимый ответ сохраняется на сервере (autosave + explicit save).
4. Может закрыть браузер и вернуться — продолжает с места остановки.
5. Финальная страница: «Тестирование завершено. Ответы сохранены.»
   Никаких баллов, red flags и рейтингов кандидату не показывается.

### 2.3. Сценарий эксперта

1. Очередь «Требует экспертной проверки» (расхождение evaluators, низкий
   confidence, hard-gate, red flag, явный запрос HR).
2. Drill-down: любой балл → вопросы → ответы → цитаты → оценки обоих evaluators →
   применённая rubric → история ручных корректировок.
3. Подтвердить / изменить балл + обязательная причина изменения.
4. Отметить ответ как «недостаточно информативный» (`NOT_ENOUGH_EVIDENCE`).
5. Утвердить отчёт → генерация индивидуальных вопросов к интервью.

## 3. Функциональные требования (FR)

### FR-1. Аутентификация и доступ
* FR-1.1 Session-based auth: argon2id для паролей, opaque session token (32 байта
  CSPRNG), в БД хранится SHA-256 хэш токена. Cookie `httpOnly; Secure; SameSite=Lax`.
* FR-1.2 RBAC с гранулярными permissions (`resource:action`), проверка на сервере
  в каждом API-обработчике; UI-скрытие не является защитой.
* FR-1.3 Кандидат аутентифицируется одноразовым токеном приглашения, обменивая
  его на session-cookie сессии теста. Кандидат не имеет доступа к админ-API.
* FR-1.4 Rate limiting: логин, обмен токена приглашения, отправка ответов, экспорт.

### FR-2. Конструктор ассессментов
* FR-2.1 CRUD должностей (`Position`) без изменения кода ядра.
* FR-2.2 CRUD компетенций и привязка к ассессменту с весами (сумма ≈ 100%).
* FR-2.3 CRUD вопросов 11 типов (§34 мастер-требований), rubric на вопрос.
* FR-2.4 Kelly-элементы и триады настраиваемы на уровне ассессмента.
* FR-2.5 Многоэтапные кейсы (`Scenario` + `ScenarioStage`).
* FR-2.6 Версионирование: `AssessmentVersion` в статусе `DRAFT` редактируем,
  `PUBLISHED` — immutable, `ARCHIVED` — недоступен для новых сессий.
* FR-2.7 Клонирование ассессмента и версии.
* FR-2.8 Активация/деактивация вопросов внутри draft-версии.

### FR-3. Движок тестирования
* FR-3.1 Сессия привязана к конкретной `AssessmentVersion`; последующие изменения
  теста не влияют на начатую сессию.
* FR-3.2 Серверный autosave каждого ответа; `AnswerRevision` — полная история.
* FR-3.3 Телеметрия ответа: время показа вопроса, первый ввод, отправка, число
  ревизий, возвраты к предыдущим вопросам, переключения вкладки (техжурнал).
* FR-3.4 Восстановление: `GET /api/sessions/:id` возвращает состояние и текущую позицию.
* FR-3.5 Дедлайн приглашения; истечение → `EXPIRED`, ответы сохраняются.
* FR-3.6 Умеренная антисписывающая защита: рандомизация порядка кейсов и
  элементов, банк эквивалентных сценариев, лимит попыток, одноразовые ссылки,
  серверное время. Без spyware, без камеры/микрофона.

### FR-4. Kelly Engine
* FR-4.1 Триады: 8 обязательных полей ответа (§4 мастер-требований).
* FR-4.2 Детекция потенциально дублирующих конструктов → вопрос кандидату
  «одно и то же или разное?»; автоматического слияния нет.
* FR-4.3 Репертуарная решётка 7–10 конструктов × 10 элементов, шкала 1–7,
  оба полюса всегда видимы, лексика без «плохой/хороший».
* FR-4.4 Laddering: 3–5 конструктов, глубина 3–5, без бесконечной рекурсии.
* FR-4.5 Аналитика решётки: расстояния E10↔E9, E10↔E1, E10↔E8, схожесть и
  кластеры конструктов, поляризация, распределение, противоречивость.

### FR-5. Оценка
* FR-5.1 Детерминированный scoring-модуль (чистые функции, unit-tested).
* FR-5.2 LLM Assessment Engine: строгая JSON Schema, structured output,
  retry, логирование, fallback, human review.
* FR-5.3 Двухэтапная оценка Evaluator A / Evaluator B, порог расхождения — настройка.
* FR-5.4 Confidence отдельно от score.
* FR-5.5 `NOT_ENOUGH_EVIDENCE` вместо нуля при отсутствии доказательств.
* FR-5.6 Hard-gates: сообщение «Критическая компетенция требует дополнительной
  проверки», без автоотклонения.
* FR-5.7 Red flags только со ссылкой на конкретный ответ и цитату.
* FR-5.8 Проверка согласованности «декларации ↔ решения в кейсах».
* FR-5.9 Работа платформы при недоступности LLM: статус `ASSESSMENT_PENDING`,
  очередь обрабатывается после восстановления; сессии не теряются.

### FR-6. Human Review
* FR-6.1 Хранить `model_score`, `human_score`, `final_score`, `review_reason`,
  `reviewer_id`, `timestamp`.
* FR-6.2 Полный drill-down любого балла.
* FR-6.3 Пересчёт итогового score после ручной корректировки — явный, с записью
  в audit log; исторические результаты не пересчитываются молча.

### FR-7. Отчёты и аналитика
* FR-7.1 Web-отчёт и PDF из 14 разделов (§45 мастер-требований).
* FR-7.2 Автогенерация 5–10 индивидуальных вопросов к интервью со ссылками на
  фактические ответы.
* FR-7.3 Сравнение до 5 кандидатов; без автоматического рейтинга по Overall.
* FR-7.4 Analytics dashboard, Calibration dashboard, статистика качества вопросов.
* FR-7.5 Benchmark-группы (top performers) с обязательной методической оговоркой.
* FR-7.6 Экспорт CSV / XLSX / PDF / JSON, объём зависит от прав.
* FR-7.7 Полнотекстовый поиск (PostgreSQL FTS, russian) по кандидатам,
  конструктам, ответам, комментариям экспертов.

### FR-8. Аудит и данные
* FR-8.1 Audit log: кто, когда, что, старое и новое значение — отдельно от
  технических логов; неизменяемая таблица (append-only, без UPDATE/DELETE в API).
* FR-8.2 Retention policy, обезличивание, экспорт данных кандидата, лог согласия.
* FR-8.3 `EmploymentOutcome` — отдельное право доступа.

## 4. Нефункциональные требования

| Область | Требование |
|---|---|
| Развёртывание | Docker Compose на собственном Linux-сервере Заказчика |
| Внешние зависимости | только LLM API (опционально; локальная модель поддерживается) |
| Доступность | отказ LLM не блокирует прохождение теста |
| Производительность | p95 сохранения ответа < 300 мс при 50 одновременных кандидатах |
| Целостность | published-версия ассессмента immutable (проверяется тестом) |
| Воспроизводимость | результат воспроизводится относительно версий test/rubric/prompt/model |
| Безопасность | OWASP ASVS L2 ориентир; см. `docs/SECURITY.md` |
| Наблюдаемость | structured JSON logs, request-id, /healthz, /readyz |
| Локализация | ru-RU в MVP; строки вынесены в словарь для будущего i18n |
| Доступность UI | контраст WCAG AA, клавиатурная навигация, табличный эквивалент всех графиков |

## 5. Acceptance criteria (§79 мастер-требований)

- [x] кандидат проходит полный тест от приглашения до финальной страницы;
- [x] прогресс сохраняется и восстанавливается;
- [x] HR получает отчёт (web + PDF);
- [x] каждый балл имеет evidence с цитатой;
- [x] human review выполняется и сохраняет model/human/final;
- [x] веса меняются через admin UI (draft-версия) с audit-записью;
- [x] ассессмент версионируется, published immutable;
- [x] новая должность добавляется данными, без изменения ядра;
- [x] данные в PostgreSQL, нормализованная схема;
- [x] запуск через Docker Compose;
- [x] automated tests (unit / integration / API / permissions / scoring / LLM schema / e2e);
- [x] инструкция backup/restore/DR;
- [x] audit log;
- [x] техническая документация в `/docs`.

## 6. Область MVP и последующих этапов

**MVP (§67):** авторизация, RBAC, две должности, приглашения, candidate test UI,
Kelly triads, repertory grid, ≥5 кейсов на должность, LLM assessment, human review,
candidate report, comparison, analytics, audit log, Docker deployment.

**Этап 2 (§68):** банк вопросов (расширенный), технический экзамен, нормативные
вопросы, численные расчёты, adaptive testing, benchmark, performance outcomes,
калибровка, расширенная аналитика.

**Этап 3 (§69):** инженер ННБ, цементирование, заканчивание, долота,
супервайзинг, координаторы — добавляются как `Position` + seed-данные.
